### Cold-worktree gotcha — three skill submodules pre-drifted (differently)

Third consecutive worktree with the drift-on-first-open pattern, but
today's shape was new: `gstack`, `marketingskills`, and
`mattpocock-skills` all showed dozens of `D` (staged-delete) lines in
`git status` even though `git ls-tree HEAD == git rev-parse HEAD` in
each. Working trees had checked out empty — likely the shared
`.git/modules/` had drifted past the working-tree checkout during a
prior session's cleanup. Fixed with a single `git reset --hard HEAD`
inside each submodule, no upstream bump needed.

Additionally `trusted-external-repos/open-design` was in a "no commits
yet" state (empty `.git` reference, working tree gone). Repaired with
a manual `git fetch origin --depth 200 main` + `git checkout
FETCH_HEAD` inside the submodule — a plain `git submodule update`
from the parent failed because the recorded pointer wasn't in the
submodule's local object database yet. Follow-on unshallow was
required for the generator's `updatedAt` timestamps.

Take-away pattern update: today's drift wasn't "recorded pointer
diverged from checkout" (past sweeps' shape); it was "working tree
empty despite matching pointer". `git reset --hard HEAD` from inside
the submodule is the fix — no need to re-inspect direction against
upstream first. Only chase upstream after the working tree is
actually there.
