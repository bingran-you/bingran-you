### Bug found and fixed: catalog links pointed at stale personal forks

`personal-site/scripts/generate-skills-data.mjs` built each skill's `githubUrl`
from a hardcoded `owner`, and for three collections that owner was a personal
fork rather than the repo the submodule actually tracks:

| Collection | Link pointed at | Fork head | Upstream head |
| --- | --- | --- | --- |
| marketingskills | `bingran-you/marketingskills` | `3df87f9` | `f557c54` |
| open-design | `bingran-you/open-design` | `05f5b33` | `18273c01` |
| gstack | `bingran-you/gstack` | `85fd9db` | `85fd9db` (in sync) |

A fork that lags upstream does not contain the newly pinned commit, so the
source link for any newly added skill 404s. This bump would have shipped
`/skills/events` linking to a path that does not exist on
`bingran-you/marketingskills`. The open-design fork is ~2 pins behind and has
been silently wrong for a while.

Fix: `owner`/`repo` now name the tracked upstream (`coreyhaines31`, `nexu-io`,
`garrytan`), matching what `mattpocock-skills` already did. Self-healing on
future bumps — no fork syncing required.

**Rule going forward:** the catalog's `githubUrl` owner must equal the
submodule URL owner in `.gitmodules`. If a new source root is added, don't
point it at a fork.
